# DECISIONS — 디자인 v2 자동 결정 기록

> 사용자가 "너가 다 알아서 해"라고 위임한 네 가지 결정을 DESIGN-GOVERNANCE §7 형식으로 기록한다.
> 기획 저장소는 수정하지 않는다. 이 기록은 `aimw-design/`에만 둔다.

---

## D-01 새 컨셉을 단일 진실로 승격

- **결정**: `aimw-design/CONCEPT.md`를 `aimw-design/DESIGN-PLAN-v2.md`로 승격해 시각 토큰의 단일 진실로 삼는다. PRD v0.6의 제품 규칙과 DESIGN-GOVERNANCE는 그대로 유지한다.
- **근거**: 사용자가 기존 UI를 "디자인이 너무 별로고 AI 티 난다"며 명시적으로 거부하고 "기존 디자인 수정말고 완전 새로"를 요구했다. 승인된 DESIGN-PLAN의 팔레트를 그대로 쓰면 거부 사유가 해소되지 않는다.
- **대안**: ① 기존 DESIGN-PLAN 토큰으로 복귀 ② 두 문서를 병합한 v3 승인.
- **거부 사유**: ①은 사용자의 명시적 거부와 충돌한다. ②는 추가 승인 대기를 만들고 위임 취지에 반한다.
- **영향**: 색·타이포·간격·반경·그리드 토큰 전부. 화면 구조는 유지.
- **후속**: 기획 저장소의 DESIGN-PLAN은 변경하지 않는다. 나중에 기획 측 승인이 필요하면 이 문서를 근거로 G4/G5 재심의.

## D-02 도구 모드 = 로컬 디자인 보드 + SVG 핸드오프

- **결정**: Figma MCP·컴퓨터 유즈 대신 브라우저 디자인 보드(`index.html`)를 1차 산출물로 쓰고, Figma 이관은 `figma/components.svg` + `figma/HANDOFF.md`로 고정한다.
- **근거**: 이 세션에서 Figma 도구 0건, MCP 리소스/템플릿 0건, 컴퓨터 유즈 도구 0건. 브라우저 자동화와 파일 쓰기만 사용 가능.
- **대안**: Figma OAuth MCP 연결을 사용자에게 요청.
- **거부 사유**: 사용자가 "다 알아서 해"라고 위임했으므로 추가 인증 요청으로 블로킹하지 않는다.
- **영향**: 10단계 중 2·3·10단계의 산출물 형태. 4~9단계는 도구와 무관하게 동일.
- **후속**: 나중에 Figma 연결이 생기면 `DESIGN-METHOD-ADAPTED.md`의 `{{TOOL_MODE}}`만 `Figma MCP`로 치환해 재실행.

## D-03 공식 검증 규칙의 도메인 조정

- **결정**: "화면당 80단어"는 서술문에만 적용하고 메타 `라벨:값`은 예외로 한다. "정보 6줄"은 라벨:값 1줄을 1개로 계산한다. 다크 모드는 만들지 않고 `ink` 배경은 로그·미리보기 패널에만 쓴다.
- **근거**: PRD DESIGN-PLAN 원칙 5는 출처·모델·비용 메타를 모든 결과물에 상시 붙이라고 요구한다. 공식의 80단어·6줄 제한을 그대로 적용하면 이 요구를 위반한다. 또한 이 제품은 라이트 단일 모드로 설계됐다.
- **대안**: 공식 수치를 그대로 적용.
- **거부 사유**: 제품 요구사항과 직접 충돌하며, 메타를 줄이면 비용·권리 투명성 훼손. 반쪽 다크 모드는 토큰 2배를 만들어 유지보수 비용만 증가.
- **영향**: 검증 규칙, 토큰 수, 화면 밀도.
- **후속**: 9단계 검증에서 조정된 기준으로 수치 보고.

## D-04 컴포넌트 1차 범위

- **결정**: 전체 인벤토리는 `COMPONENT-SPECS.md`의 90여 개를 그대로 등록하되, 1차 구현·검증 대상은 핵심 10개로 제한한다.
- **근거**: 사용자가 "컨셉이랑 컴포넌트랑 핵심 디자인만 만들어보자"라고 범위를 명시했다. 90개를 한 번에 만들면 이전 구현의 실패를 반복한다.
- **대안**: 공식의 20~25개 전부 구현.
- **거부 사유**: 사용자 명시 범위 초과, 검증 가능성 저하.
- **영향**: 6·7·9단계 산출물.
- **후속**: 이후 모듈 추가 시 핵심 10개를 먼저 재사용하고 부족한 것만 Expansion.

## D-05 전용 도구 화면과 공통 톤의 분리

- **결정**: v1의 동일한 "작업기록장 행" 레이아웃을 버리고, 10개 모듈을 각각 전용 도구 화면으로 재구성하되 토큰·헤더·모듈 띠·검상 패널은 공유한다.
- **근거**: 사용자가 "각 기능이 주력인 사이트 같은 거지, 단 톤은 맞춰야 한다"고 명시했다.
- **대안**: ① 모듈별 완전 별도 디자인 시스템 ② v1 행 레이아웃 유지.
- **거부 사유**: ①은 톤 불일치로 사용자가 거부한 방향. ②는 기능 구분이 안 돼 사용자가 거부한 방향.
- **영향**: S0~S9 내부 레이아웃과 시각 어휘. 제품 규칙과 토큰은 변경 없음.
- **후속**: `aimw-app/DESIGN-V2.md`를 구현 기준으로 유지.

## D-06 자연어 진입과 예시 실행 통제

- **결정**: 전체 챗봇을 상단 고정 진입점으로 두고, 현재 모듈에 맞는 예시 문장을 함께 보여준다. 모듈별 별도 봇은 만들지 않는다. 예시를 눌러도 **입력창에만 채우고**, 사용자가 `요청하기`를 눌러야 화면 이동과 선택값 준비가 실행된다.
- **근거**: 사용자가 비전공자도 쉽게 쓰길 원하면서도 "예시가 바로 챗봇에 입력되어 바로 작동하면 통제성이 떨어진다"고 우려했다.
- **대안**: ① 예시 클릭 즉시 전송 ② 모듈마다 별도 AI 챗봇 생성.
- **거부 사유**: ①은 사용자가 지적한 통제성 문제가 그대로 남는다. ②는 현재 도구 환경에서 외부 AI 연결을 전제하게 되어 규칙(외부 호출 없음)과 충돌하고, 톤도 분리된다.
- **영향**: CommandDock 동작, v5 사용성 부록, 구현 기록.
- **후속**: 실제 AI 모델 연결이 승인되기 전까지는 로컬 규칙 기반 파서 상태를 유지한다. 지원 범위 밖 문장은 수집함으로 보내고 예시를 다시 안내한다.

## D-07 영상·글 부분 수정의 범위 표현

- **결정**: 영상은 전체 영상 / 구간(씬) / 프레임(콘티) 3종을 선택하게 하고, 글은 드래그·마크·줄 셀 3종으로 부분을 지정한다. 수정 요청은 기록으로만 남기고 사람이 승인한다.
- **근거**: 사용자가 전체 재생성 없이 부분별 선택·수정을 요구했다.
- **대안**: ① 텍스트 입력으로만 수정 요청 ② 요청 즉시 자동 반영.
- **거부 사유**: ①은 비전공자가 범위를 표현하기 어렵다. ②는 사람 승인과 게이트 규칙을 우회한다.
- **영향**: S2, S8 화면과 데이터 기록 형태. 게이트·권리·동의 규칙은 변경 없음.
- **후속**: `DESIGN-PLAN-v5-EASE.md` §4~§5를 화면 검증 기준으로 사용.
