# DECISION-LOG — 의사결정 기록

작성일: 2026-11-22  
범위: AIMW 분석·설계 단계에서 내린 결정과 근거. 날짜순 + 주제별.  
표기: 결정의 변경은 새 항목을 추가하고 이전 항목은 "대체됨"으로 표시한다.  
서술 규칙: 저장소에 포함되지 않는 캡처 자료의 경로·파일명·링크·스크린샷 위치는 기재하지 않는다. 근거는 **로컬 캡처 분석 결과(저장소 미포함)를 일반 원칙으로 정리**해 적는다. 서비스명·점수·순위는 기존 감사 맥락을 유지하되, 특정 앱의 기능을 그대로 구현한다는 표현은 쓰지 않는다.

## A. 분석 범위·출처 결정

### A1. 캡처 자료는 읽기 전용, 산출물은 기획 문서에만 저장
- **결정**: 캡처 자료는 수정하지 않는 Golden Source로 두고, 모든 결과물은 기획 문서에만 저장한다.
- **근거**: 사용자 요구. 원본 캡처의 해시/메타 보존 필요. 캡처는 이 저장소에 포함되지 않으므로 문서에서 경로·파일명으로 의존하지 않는다.
- **대안**: 원본에 주석 추가(기각 — 감사 추적 훼손).

### A2. 전체 자료 해시 인벤토리 생성
- **결정**: 파일 수/용량/유형/역할/SHA-256을 별도 소스 인벤토리(사용자 관리)에 전수 기록한다.
- **근거**: 누락·중복·출처 판별의 기초 데이터. 중복 해시 그룹과 0KB 스텁을 식별했다.
- **영향**: 일부 서비스의 안내 문서는 생성 코드가 아닌 보조 산출물로 재분류(수정 반영 완료).

### A3. 생성 코드와 원본 캡처의 엄격 분리
- **결정**: 특정 서비스의 생성 재구성물과 검증 산출물은 "Craft Anything 생성물"로만 취급, 원본 소스로 인용 금지.
- **근거**: 생성 품질 검증 결과 약 58% 유사도·28/36 claims, 단순 복사 스크립트, 플레이스홀더 이미지, 타 서비스 오염 FAQ.
- **영향**: 해당 서비스는 패턴 참고만, 직접 코드 재사용 0건 원칙 확립.

### A4. Motion 레퍼런스 — 진본 재분류 (재캡처로 일부 철회)
- **최종 결정**: 오귀속 자료는 계속 전면 제외하되, **로컬 캡처 분석 결과(저장소 미포함)에서 확인된 Motion 진본 캡처를 패턴 근거로 허용**한다.
- **재캡처 근거**: 로컬 캡처 분석 결과(저장소 미포함)에서 Motion 진본 캡처가 확인되었다. 기존 오귀속 판정은 서비스 간 자료 혼동에서 비롯된 것이며, 진본 캡처의 안내 문구도 Motion 랜딩임을 명시한다.
- **초기 판정(철회)**: 텍스트·메타·이미지 해시·치수가 다른 서비스 것이라 전체를 제외했으나, 원인은 **서비스 간 캡처 자료 혼동**이었다.
- **허용 범위**: Inter Variable 계열 서체, 남색/연회색 배경, visual-first 리포트, 자동 그룹화, AI 태깅, 주간 모멘텀 배지만 참고. 자산·UI 복제 금지, 내부 리포트 동작은 API 호출 기록이 없어 미단정.
- **파급**: 조합 점수 문서 Motion 0.00 → 3.70, 통합 감사 등급 X → B, 기능 매트릭스·디자인·아키텍처 문서 동기화. A5의 특정 라우트 제외도 철회.

### A5. 오귀속 자료 추가 제거
- **결정**: 일부 서비스의 상태 캡처(다른 서비스 URL), 오염된 가이드 문서, SHA가 동일한 중복 상태 캡처를 근거에서 제외. Creatify의 특정 에이전트 라우트는 A4 재캡처로 **Motion 진본 재분류**에 따라 제외 철회.
- **근거**: 로컬 캡처 분석 결과(저장소 미포함)의 출처 정보와 해시 대조.
- **영향**: affected 서비스의 상태 기반 UI 서술 신뢰도 하향, 렌더 텍스트/구조 기반으로 대체.

### A6. 이미지 직접 판독 불가 한계 명시
- **결정**: 스크린샷 시각 묘사를 "픽셀 관찰"이 아닌 "렌더링 텍스트·구조·OCR 기반 증거"로 표기.
- **근거**: 모델의 이미지 입력 미지원, 로컬 캡처 분석 결과(저장소 미포함)에서도 동일 한계가 확인됨.
- **대안**: OCR과 해시/헤더 검증으로 보완. 향후 이미지 입력 가능 에이전트에 재위임 권고.

## B. 제품·설계 결정

### B1. P0 F1~F7 정의 확정 및 재대조
- **결정**: F1 레퍼런스 분석 → F2 콘텐츠 기획 → F3 콘텐츠 제작 → F4 검수 → F5 발행 → F6 성과 분석 → F7 개선.
- **근거**: 사용자 정의를 서브 분석의 임의 F ID 매핑보다 우선.
- **영향**: 통합 감사, 기능 매트릭스, 화면 설계 문서 전부 재대조 완료.

### B2. 조합 점수 가중치 고정
- **결정**: P0 적합성 30 / MVP 구현 25 / UI·UX 20 / 유지보수·확장 15 / 연동·운영비용 10.
- **근거**: 사용자 요구. 합계 100%.
- **결과(최초)**: Snipit 4.50 > Buffer 4.10 > MONOV 3.80 > Creatify 3.55 > Foreplay 3.15 > Postiz 2.90, Motion 제외(0.00).
- **결과(재캡처 반영)**: Snipit 4.50 > Buffer 4.10 > MONOV 3.80 > **Motion 3.70** > Creatify 3.55 > Foreplay 3.15 > Postiz 2.90. 가중치는 변경 없음.
- **영향**: 상위 2개(Snipit/Buffer)가 IA·F1·F5~F7 주 축, MONOV가 F3 축, Creatify가 F2/F3/F4 보조. **신규 모듈 S8·S9은 자체 설계이며 이 점수표·순위에 포함하지 않는다.**

### B3. 채택 분류 5종 사용
- **결정**: 직접 코드 재사용 / 공식 API·MCP 연동 / UI·UX 패턴 참고 후 자체 구현 / 후속 개발 / 제외.
- **결과**: 직접 코드 재사용 0건, 패턴 참고 후 자체 구현이 MVP 기본.
- **근거**: 라이선스 미확인 + 오귀속 + 품질 문제.

### B4. 디자인 토큰 "재선언" 원칙
- **결정**: 관찰된 원본 값은 참고 기록으로만 두고, 통합 팔레트는 별도 값으로 재정의한다.
- **근거**: 트레이드드레스/표현 저작권 리스크 + 여러 브랜드 톤의 혼재.
- **영향**: 디자인 설계 문서, 조합 점수 문서의 디자인 섹션.

### B5. AI는 비동기 Job + 사람 승인
- **결정**: 모든 생성은 Job 상태(queued→…→approved→published)로 추적, 승인 전 발행 비활성.
- **근거**: 사람 승인 원칙, 게시물 큐의 상태 밀도, 운영 신뢰.
- **영향**: 아키텍처 JobRunner, 컴포넌트 명세의 승인 게이트/JobDrawer.

### B6. 발행/과금 Dry-run
- **결정**: MVP에서 실제 전송·결제 없이 상태/UI만 재현, Dry-run 배지 상시 표시.
- **근거**: 사용자 요구(외부 API 실행/과금 금지), OAuth·인프라 비용.
- **영향**: 요구사항 범위 외, 화면 설계의 발행 화면.

## C. 기술·운영 결정

### C1. 로컬 Ollama를 기본 추론 Provider로 확정
- **결정**: `qwen3.8-local:latest`(Qwen 27B UD-Q4_K_M + mmproj F16), 로컬 추론 엔드포인트, ctx 4096, 동시 추론 1개.
- **근거**: 설치·해시·API 테스트 완료. VRAM 7.6/8GB.
- **대안**: 유료 API 우선(기각 — 비용/키 관리, 사용자 승인 전).

### C2. 스택 선택: React/TS + shadcn/Tailwind v4 + FastAPI + SQLite
- **결정**: MIT/무료 OSS 조합.
- **근거**:(headless 테이블, React 차트, FastAPI, Pydantic, SQLite) 모두 라이선스·React/TS 적합성 확인.
- **선행 조건**: npm/bun 미설치 → Node 설치 후 shadcn 초기화 필요.

### C3. Postiz/Buffer는 연동만, 포크/내장 금지
- **결정**: AGPL-3.0 소스공개 리스크 → REST/MCP 연동만 검토, 코드 포크 보류.
- **근거**: OSS 라이선스 리서치(자체 호스팅에 Postgres/Redis/Temporal 필요).
- **영향**: 조합 점수 문서의 제외 항목.

### C4. 워크플로/렌더 도구의 운영 경로 제한
- **결정**: n8n은 내부 백그라운드 자동화로 제한(사용자용 워크플로 빌더 금지), GPL 파생 이미지/영상 처리 도구와 무가드 코드 실행 도구의 웹 서비스화는 보류.
- **근거**: OSS 라이선스/보안 리서치.
- **영향**: S8 실제 변환·합성 어댑터는 Phase B/C 또는 제외(A4 연장).

### C5. 디자인 스킬 미설치 → 수동 체크리스트 + 브라우저 검수 대체
- **결정**: 외부 디자인 스킬 모두 미설치로 확인, 가용한 브라우저 스킬로 렌더링·접근성·콘솔 검수.
- **근거**: 세션 사용 가능 스킬 제한.
- **영향**: 디자인 설계 문서의 가용성 표 기록.

### C6. 구현 착수 전 환경 세팅을 착수 전 단계에 편성
- **결정**: Node/npm, Python venv 설치를 실행 계획의 사전 환경 절에 명시.
- **근거**: 캡처 빌드가 node/bun 부재·consent_required로 무산된 이력.

## D. 문서 결정

### D1. 기획 문서 11개 구조 확정
- **결정**: 감사·조합·기능 매트릭스 4개, 디자인 3개, 루트 4개(요구사항/아키텍처/실행 계획/결정 기록) 구조.
- **근거**: 사용자 요구 목록.
- **현황**: 전 문서 작성 완료, 상호 참조 일관성 검증 필요(최종 체크).

### D2. 실제 웹앱 코딩은 하지 않음
- **결정**: 분석·계획·설계 문서만 저장하고 종료.
- **근거**: 사용자 요구(구현은 별도 착수).
- **상태**: 준수 중 — 기획 문서에는 마크다운만 존재.

### D3. 저장소 미포함 자료에 대한 경로 의존 배제
- **결정**: 캡처 자료는 저장소에 푸시되지 않아 다른 작업 환경에 존재하지 않는다. 따라서 5개 대상 문서에는 캡처 경로·파일명·링크·스크린샷 위치·"특정 분석 파일에서 참고"·"특정 앱 기능 구현" 서술을 넣지 않는다.
- **근거**: 사용자 명시 최우선 제약. 근거가 필요하면 로컬 캡처 분석 결과(저장소 미포함)를 일반 원칙으로 정리한다.
- **영향**: 서비스명·점수·순위는 유지, 표의 "근거" 열은 일반 원칙 설명으로 대체.

## E. 수집 파이프라인 결정 (사용자 결정 반영)

### E1. 캡처는 참고용, 수집·검색·분석은 자체 설계·구현
- **결정**: 캡처는 인터랙션/토큰 참고용으로만 두고, "분야/우리 서비스/경쟁사 등록 → 수집 → 정리 → AI 분석" 파이프라인은 이 프로젝트용으로 새로 설계한다.
- **근거**: 사용자 명시. 캡처는 마케팅 사이트 렌더링일 뿐 실제 수집 엔진·API가 없음(API 호출 기록 없음).
- **대체됨**: 기존 실행 계획·아키텍처의 "외부 스크래핑은 MVP 범위 밖" 방침은 이 결정으로 대체됨. 발행 Dry-run 원칙(B6)은 유지.
- **영향**: S0 Collector 화면 신설, 요구사항 FR-02~FR-06, 아키텍처 CollectorHub. 이후 S5~S8이 추가되었고, **S9 추가로 최종 10개 화면 라우팅**.

### E2. MVP 수집 범위 — 4개 파트 UI + 제한된 어댑터
- **결정**: 영상 광고 / 이미지 광고 / 블로그 / 뉴스 4개 수집 파트를 독립 탭(URL)으로 노출하고(별도 '전체' 집계 탭을 더해 5탭), 어댑터는 수동 입력 + RSS + 공식 API 1~2개(키 발급 시)로 제한. 나머지는 "연동 대기" 배지.
- **근거**: 1~2일 현실성(당시 추정 약 11~12시간, 현재 기준 14~16시간 상한 — `IMPLEMENTATION-PLAN.md` 참조), 키/심사 소요, 법적 리스크.
- **영향**: 실행 계획 #4~#8, 화면 설계 S0.

### E3. 1차 소스 4개 확정
- **결정**: YouTube Data API(영상+썸네일), 네이버 검색 API(한국어 뉴스+블로그), RSS/Sitemap(블로그), GDELT classic(영문 뉴스 백업)을 1차로 사용.
- **근거**: 공식 문서상 무료·심사 불필요(YouTube/네이버는 키만), 할당량 명확(YouTube 약 10,000 units/day + 검색 약 100/day, 네이버 25,000/day). 구글 뉴스 RSS는 개인·비상업용이라 제외.
- **영향**: 아키텍처 소스 표, 요구사항 가정/의존.

### E4. 광고 라이브러리는 "메타데이터만, 연동 대기"
- **결정**: 심사·토큰 완료 후 메타데이터/스냅샷 식별자만 적재. MVP에서는 실제 호출 없이 상태만 표시. Google Ads Transparency는 공식 상업 API가 확인되지 않아 공개 데이터셋 검토로 유보.
- **근거**: 신원확인 수일, 심사·지역 한정, OAuth, 자동 수집 ToS 금지.
- **영향**: 요구사항 범위 외, 아키텍처 연동 대기 표.

### E5. 스크래핑 금지선과 오픈소스 선택
- **결정**: 캡차 해결·지문 위조·프록시 회전·로그인 쿠키 공유 도구 사용 금지. 피드 파서/본문 추출/HTML 파서 계열의 허용 라이선스 조합 사용. 브라우저 렌더는 Python 기반 선택적 사용.
- **제외**: AGPL 코어 셀프호스트, 미디어 다운로더, 유료 Actor, 라이선스 없는 스크래퍼, 비상업 제한 피드, GPLv3 문서 변환기.
- **영향**: 아키텍처 소스 표, 컴포넌트 명세 재사용 금지 목록.

### E6. 자동화 도구는 개발 보조, 운영 경로는 REST/라이브러리
- **결정**: MCP·에이전트 도구는 개발 중 셀렉터/스키마 탐색에만 쓰고, 확정 스키마는 FastAPI 라이브러리 호출로 고정. 웹앱 요청 경로에 MCP를 두지 않는다.
- **근거**: 세션/컨텍스트/비결정성 비용, 제공자 정책·AGPL 리스크.
- **영향**: 아키텍처 도구 경계 표.

### E7. 미디어 비재호스팅 + provenance 보존
- **결정**: 이미지·영상 파일을 내려받아 재배포하지 않고 원문/썸네일 식별자만 참조. 모든 수집 항목에 출처, 방식, 수집 시각, 약관 스냅샷, 라이선스 메모를 저장.
- **근거**: 광고 크리에이티브·뉴스 사진·헤드라인의 저작권/상표/퍼블리시티 권리.
- **영향**: 아키텍처 데이터 계층, 요구사항 NFR-09.

## G. S8 비디오 워크벤치 결정 (사용자 추가 기획 반영)

### G1. S8은 S2의 서브탭이 아니라 독립 모듈
- **결정**: S8 Video Workbench는 별도 라우트·별도 3탭 상태(분석/제작/수정)·별도 Job으로 구성하고, S2 Studio에 서브탭으로 붙이지 않는다.
- **근거**: S2는 텍스트/이미지 브리프·카피 중심, S8은 영상 분석·콘티·3D 구도·애니매틱·렌더 중심으로 상태 수명과 산출물이 다르다. 모듈 엉킴 방지 원칙(F2)을 그대로 적용.
- **연결**: 사용자가 "참고로 가져오기"를 누를 때만 `ModuleLink(s8→s2)` 생성. S2 상태 재사용·자동 동기화·FK·데이터 복제 없음.
- **영향**: 실행 계획 10개 라우트, 3탭 독립 상태.

### G2. 제작 유형 6종 — 프로젝트 단위 명시 선택
- **결정**: S8 프로젝트의 제작 유형을 `실사 / 숏폼 / 영화 / 영상 / 애니메이션 / 모션그래픽` 6종으로 정의하고, **프로젝트 단위로 사용자가 명시적으로 1개를 선택**한다. **기본값은 미선택**이며, **자동 감지·자동 변경을 금지**한다(변경 시 사용자 재확인).
- **근거**: 유형에 따라 분석 차원·구도·게이트 산출물·템플릿·비용 프로파일이 달라지므로, 추론으로 정하면 4단계 게이트 전체가 잘못된 가정 위에서 진행된다.
- **적용 범위**: 선택 값이 2계층 분석의 차원 필터, 3D 구도 스키마, 각 게이트 산출물, 템플릿 필터, 비용 프로파일을 결정한다. Phase A에서는 **템플릿 필터/샘플 프리뷰**까지만 노출한다.
- **참조**: 제작 유형별 명세, 자체 숏폼 구성·모션그래픽 지식(모두 별도 관리).
- **효과**: 캡처 서비스의 점수·순위에는 영향 없음(자체 설계).

### G3. 2계층 분석(콘텐츠 + 기술)
- **결정**: 분석 탭은 콘텐츠 분석(훅·메시지·CTA·톤)과 기술 분석(카메라앵글·기법·전환·조명·구도·편집)을 **별도 스키마로 동시 기록**하고, 제작 유형에 따라 강조 차원을 필터링한다.
- **근거**: 비전문가 설명과 전문 용어가 섞여 들어오므로 한 층만 두면 재작업이 발생한다.
- **영향**: S8 분석 스키마/UI, `TermMapping` 입력.

### G4. 자연어 → 용어 매핑은 사용자 확인 게이트
- **결정**: 비전문가 자연어 문장은 `TermMapping`(표준 용어 + 원문 근거 + 지식베이스 안정 ID)으로 변환한 뒤 **사용자 수정·확정**을 거쳐야 다음 단계로 진행한다. 미확정이면 콘티 게이트 잠금.
- **근거**: 오매핑이 4단계 전체에 전파되는 비용이 크다. 사람 승인 원칙(B5)의 연장.
- **영향**: 확인 게이트 UI, 용어 사전 설정.

### G5. 4단계 게이트 + 전체 자동 렌더 없음
- **결정**: 제작 흐름은 ①콘티 → ②3D 구도 스키마 → ③애니매틱 → ④단계별 렌더의 4게이트로 고정하고, 각 단계는 명시적 승인 후에만 다음으로 넘어간다. MVP에서는 드라이런 어댑터 샘플 프리뷰만 제공하고 **전체 자동 렌더·모션 내보내기는 실행하지 않는다**. `PRE-0a/0b` 사전 확인 단계는 게이트 수에 포함하지 않으며 승인 게이트는 G1~G4 4개다(J-31).
- **근거**: 렌더 비용·지연·품질 리스크, Phase A 범위, 검증되지 않은 외부 생성 API를 호출하지 않는다는 제약.
- **영향**: 실행 계획 Day 2 작업 / 체크리스트, Phase B/C 이관.

### G6. 수정은 샷/타임코드 타겟
- **결정**: 수정 탭은 샷 ID/타임코드를 선택해 해당 구간만 개정 요청·프리뷰하고 개정 메모를 샷 단위로 저장한다. 전체 재렌더는 자동 트리거하지 않는다(diff 재렌더·유형별 모션 재내보내기는 Phase B/C).
- **근거**: 반복 렌더 비용과 변경 영향 범위의 가시성 확보.

### G7. S8 단계 분리 (Phase A / B / C)
- **결정**: Phase A = 제작 유형 선택 UI/모델/템플릿 필터, 분석 스키마 UI, 용어 확인 게이트, 4단계 샘플 게이트, 샷 단위 수정 프리뷰, 용어 사전 설정, 미디어 소스/변환/합성 스키마·권한 게이트·before/after·비용 미리보기(이하 G10~G12). **Phase B = 실제 렌더 어댑터 + 경량 3D 구도 프리뷰 + diff 재렌더 + 유형별 실제 렌더/모션 내보내기 + 실제 이미지/영상 변환·합성 어댑터.** Phase C = 실제 3D, 고품질 렌더/ML 기반 제안, 웹서비스형 이미지/영상 처리. 공급자·라이선스·예산 미확정 시 해당 어댑터는 **제외** 유지.
- **근거**: 1~2일 상한 + 렌더/변환 공급자·예산·엔진 미확정.
- **영향**: 실행 계획의 현실성 판정·작업 표·위험 표·다음 단계.

### G8. 전문 지식베이스는 자체 저작 (캡처 근거 아님)
- **결정**: 자체 지식베이스에 공개된 권위 있는 영화·광고 자료를 출처로 삼아 **자체 작성 지식**을 둔다. 원문을 그대로 복제하지 않고 요약·재서술하며, 출처 레지스트리와 권리 메모를 함께 관리한다. 엔트리는 RAG 친화적 **안정 ID**를 갖고, 한국어 비전문가 표현 ↔ 표준 용어 매핑을 포함한다. 숏폼·모션그래픽 공식 스펙도 이 새 자체 출처에서 가져온다.
- **근거**: 로컬 캡처 분석 결과(저장소 미포함)는 마케팅 사이트 렌더링일 뿐 촬영·편집 지식의 근거가 아니다. 표현 저작권/인용 리스크 회피.
- **금지**: 캡처 자료를 지식베이스 출처로 등록하지 않음, 경쟁사 문구 verbatim 복제, 근거 없는 용어 단정.
- **상태**: 자체 지식베이스 작성 완료(`knowledge/**`, 경로·파일명 없이 일반 원칙만 참조).

### G9. 레퍼런스 서치 — 자동/수동 이원화, 공개 범위 한정
- **결정**: S8 분석 탭에 **자동 검색(사용자가 트리거하는 공개 소스 검색)** 과 **수동 입력(URL·메모·타임코드)** 을 함께 둔다. 검색은 제작 유형 6종별 **검색 축**을 적용한다.
- **공개 범위**: 공식 API·공개 피드·공개 메타·수동 입력만 허용. 로그인/유료벽/스크래핑 우회(캡차·지문·프록시·쿠키 공유)는 제외한다(E5 원칙 연장). 미디어 바이트는 저장하지 않고 **provenance(출처·방식·수집 시각·약관 스냅샷)** 만 보존한다(E7 연장).
- **자동 링크 금지**: S0 Collector 결과는 사용자가 "S8로 가져오기"를 누를 때만 `ModuleLink(s0→s8)` 생성. S0→S8 자동 동기화·데이터 복제·공유 FK 없음.
- **Phase 분리**: Phase A는 검색 UI + 수동 입력 + 어댑터 스텁/샘플 결과 + 명시적 링크까지. **실제 API 호출·쿼터 운영은 Phase B**다.
- **참조**: 자체 레퍼런스 검색 플레이북(별도 관리, 일반 원칙만 참조).
- **효과**: 레퍼런스 서치 체계도 자체 설계이며 캡처 서비스 점수·순위에 영향 없음.

### G10. 입력 소스 모드 3종 — 자체 설계 기능
- **결정**: S8 입력 소스를 `generate_new` / `transform_source` / `composite` 3종으로 정의하고, 프로젝트 단위 명시 선택(기본 `generate_new`)으로 둔다. 자동 전환 금지. `transform_source`·`composite`는 사용자가 실제 사진·이미지·영상을 직접 업로드한 뒤에만 활성화한다.
- **근거**: 생성만 지원하는 워크벤치로는 실제 자산의 변환·수정·합성 수요를 담을 수 없다. 단, 소스 선택이 잘못되면 권한·비용·결과 해석이 함께 틀어지므로 명시 선택 원칙(G2)을 그대로 적용한다.
- **효과**: 캡처에 대응하는 기능이 없는 **자체 설계**이며 점수·순위에 영향 없음.

### G11. 변환·합성 범위와 4게이트 유지
- **결정**: 이미지는 크롭/색보정/배경 제거·교체/객체 편집/업스케일/스타일 변환, 영상은 트리밍/리타이밍/그레이딩/배경 교체/객체 제거/스타일 변환/프레임 보간, 합성은 레이어(배경·인물·제품·텍스트·로고·이펙트) + 마스킹 + 블렌딩 + 레이어 타이밍을 **조작 스키마·샘플 프리뷰**로 제공한다. 결과물은 **기존 4게이트(G5)를 그대로 통과**하고, before/after 비교와 샘플 단가 기반 비용 미리보기를 표시한다.
- **Phase 분리**: Phase A는 스키마·샘플·드라이런만. 실제 변환·합성 어댑터와 웹서비스형 이미지/영상 처리는 Phase B/C 또는 제외(G7). 실제 결제·청구 경로 없음.
- **근거**: 실제 처리 공급자·라이선스·예산이 확정되지 않았고, 검증되지 않은 외부 API를 호출하지 않는다. 게이트 변경은 검수 신뢰도를 훼손한다.

### G12. 권한 게이트와 타사 미디어 메타데이터 전용
- **결정**: 업로드·변환·합성 전에 `rights_flag`와 `rights_confirmed_by`를 필수 확인하고, 미확인이면 미리보기를 잠근다. 타사 레퍼런스 미디어는 **메타데이터 전용**(출처·식별자·약관 스냅샷)으로 두고 **프레임 다운로드·프레임 분석을 금지**한다(E7 연장). 권한 판정 주체는 확정 전까지 보류(J장).
- **근거**: 인물·제품·로고가 포함된 미디어의 초상권·상표권·저작권 리스크, 이미지 직접 판독 불가 한계(A6).

## H. S9 SEO & Search Growth 결정 (사용자 추가 기획 반영)

### H1. 독립 모듈 — 별도 라우트, 기본 "연결 안 함"
- **결정**: S9 SEO & Search Growth는 S6 Forecast와 **별도 라우트**로 두고, 4서브탭(**진단 / 키워드·콘텐츠 / 예산·예측 / 취합·개선**)을 가진다. 기본값은 **"연결 안 함"**이며 S2·S5·S6 상태를 재사용하지 않는다.
- **기능 범위**: 기술·온페이지·콘텐츠 진단, 키워드 갭·검색 의도 매핑, 제목/메타/구조 개선안, SERP 추적(공식 데이터 한정), SEO 투자비용↔성과 예측(CPC/CAC/ROAS/유입), 예산 배분 추천, 취합 대시보드, 개선 루프.
- **연결**: 개선 루프는 사용자가 "브리프 만들기"/"콘텐츠 만들기"를 누를 때만 `ModuleLink(s9→s2)` / `ModuleLink(s9→s5)` 생성. 자동 개선 실행·자동 주입 없음.
- **근거**: S6은 temporal 성과 예측, S9는 검색 유입·키워드·온페이지 진단으로 데이터와 상태 수명이 다르다. 모듈 엉킴 방지(F2) 적용.
- **효과**: 자체 설계이며 캡처 점수·순위에 영향 없음.

### H2. 공개·공식 데이터 한정
- **결정**: 허용 범위는 **소유 확인된 검색 콘솔 계정, 광고 계정의 공식 키워드 도구, 공식 검색 API, 공개 피드/메타, 수동 입력**뿐이다. **스크래핑·로그인 우회·유료벽 우회는 금지**한다(E5·E7 연장).
- **Phase 분리**: Phase A는 수동 입력 + 샘플 + 룰 기반 진단/예측 + Dry-run(실제 호출 없음). Phase B는 공식 API 연동 + statsmodels/scikit-learn 회귀. Phase C는 ML 최적화 + 포털 확장.
- **근거**: 계정 소유·권리 확인과 쿼터 승인 없이 외부 데이터를 가져올 수 없음. 사용자 명시(외부 API 실행 금지).
- **효과**: SERP 데이터 출처 권리와 포털 우선순위는 확정 전까지 보류(J장).

### H3. 예측은 예측 배지, 실행은 Dry-run
- **결정**: CPC/CAC/ROAS/유입 예측과 예산 배분 추천에는 항상 `예측/신뢰도/모델/기간` 배지를 붙이고, Phase A 샘플에는 `샘플` 배지를 별도로 추가한다(J-31). Phase A 집행 화면은 Dry-run이며 실제 예산 집행·광고 계정 변경·외부 전송을 하지 않는다.
- **근거**: 예측값 오인 방지(F4)와 외부 API 실행 금지(B6 연장).

### H4. S6과 데이터 복제 없음
- **결정**: S9은 S6의 시계열·지표를 복제하지 않고 필요한 값만 참조한다. 데이터 이관·공유 FK·자동 동기화 없음. 연결은 명시적 `ModuleLink`로만 생성한다(F2).
- **근거**: 지표 이중 관리로 인한 불일치와 모듈 엉킴 방지.

### H5. 자체 설계 — 캡처 점수·순위에 미포함
- **결정**: S9는 캡처에 대응하는 기능이 없는 **자체 설계(레퍼런스 점수 아님)** 로 분류하고, 조합 점수 문서의 7개 서비스 표·점수·순위에 넣지 않는다. 레퍼런스 자료에는 SEO 전용 캡처가 없다.
- **영향**: 기존 순위(Motion 4위 3.70, Creatify 5위 3.55, Foreplay 6위, Postiz 7위)는 변경하지 않는다.
